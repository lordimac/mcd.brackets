# CLAUDE.md

Turnierverwaltung (Single/Double Elimination, Round Robin) mit Event-basiertem Meisterschafts-Punktesystem. Express-Backend auf Basis von `brackets-manager`, Vanilla-JS-Frontend mit `brackets-viewer`.

## Befehle

```bash
npm install
npm run server         # Dev-Server (tsx src/server.ts) → http://localhost:3000
npm run server:watch   # Dev mit tsx watch Auto-Reload
npm test               # Node-Testrunner über tsx (src/**/*.test.ts)
npm run build          # tsc (TypeScript 7, nativ) → dist/ — Typprüfung inkl. Tests
npm start              # node dist/server.js
npm run vendor         # kopiert brackets-viewer, html2canvas, jsPDF aus node_modules nach public/lib/
npm run docker:rebuild # Image bauen + Container mcd-brackets neu erstellen (Port 3001, ./data)
```

- **Nach jeder abgeschlossenen Änderung `npm run docker:rebuild` ausführen** (Wunsch des Users). Port 3000 ist durch einen anderen Container belegt. Das Skript baut über den buildx-Builder `mcd-dns` mit festen DNS-Servern (`scripts/buildkitd.toml`), weil die DNS-Auflösung in Docker Desktop hier nicht funktioniert und `docker build`/`docker compose build` bei `npm ci` hängen bleiben.

- Umgebungsvariablen: `PORT` (3000), `DATA_DIR` (`./data`), `ADMIN_PASSWORD`, `UPDATE_CHECK` (`false` = kein Versionscheck), `TRUST_PROXY` (Express `trust proxy`, Default aus). Für manuelle Tests einen Server mit eigenem `DATA_DIR` und Port starten, nie gegen die echte `data/db.json` schreiben.
- Nach jedem Update von brackets-viewer/html2canvas/jspdf `npm run vendor` ausführen — der Browser lädt nur die Kopien in `public/lib/`.
- Node 24 LTS (`.nvmrc`, `engines`, Docker `node:24-alpine`; `docker:rebuild` baut mit `--pull`). Container läuft als `node` (UID 1000).
- TypeScript 7 hat keine JS-Compiler-API mehr → kein `ts-node`; Ausführung von TS-Dateien über `tsx`.
- `package.json` erzwingt per `overrides` `uuid@^11.1.1` (Sicherheitsfix für brackets-manager).
- `brackets-model` ist devDependency, nur für Typen (`import type`); Ausnahme: Tests importieren `Status`.

## Architektur

**Backend** (`src/`):
- `db.ts`: `JsonDatabase` (brackets-json-db → node-json-db, hält Daten **im Speicher**) auf `DATA_DIR/db.json`, typisiert als `CrudInterface` (die eigenen Typen von JsonDatabase sind zu lose). Immer über `getStorage()`/`getManager()` zugreifen, nie Instanzen cachen — `replaceDatabase()` erzeugt sie neu. `withLock()` serialisiert alle schreibenden Routen, `withRollback()` stellt bei Fehlern den Snapshot wieder her.
- `server.ts`: Routen. Fehler per `throw new HttpError(status, msg)`; Express 5 leitet abgelehnte Promises an den JSON-Error-Handler am Ende weiter (keine try/catch in Routen nötig).
- `stages.ts`: `createStage()`/`deleteStage()`/`findStage()` — gemeinsame Bausteine für Anlegen, Neu-Erzeugen und Löschen. Beim Ergänzen von `event_name` die Stage **frisch aus dem Storage lesen**: das Rückgabeobjekt von `create.stage` hat kein `settings.seedOrdering`, ein Zurückschreiben würde es löschen und Double Elimination unspielbar machen (Regressionstest `stages.test.ts`).
- `lan.ts` (reine Logik), `lan-store.ts` (Persistenz), `lan-routes.ts` (Router unter `/api`): Events mit Domain, DNS-Server und 3 IP-Bereichen; Teilnehmer (`attendee`) mit `slot` → IP *i* = `ranges[i].start + slot`, DNS-Namen `hostname`, `hostname2`, `hostname3` (+ `.domain`). Nickname und alle abgeleiteten DNS-Namen sind je Event eindeutig. Tabellen `event`/`attendee` liegen in derselben `db.json` (über `getAppStore()`, `ensureAppTables()` legt sie an). `syncEventsFromStages()` erzeugt Event-Datensätze für alte Turniere (beim Start und nach Restore).
- Bulk-Import `importBulk()`: Zeilen `Nachname, Vorname // Clan-Nickname` (`parseBulkLine`), jede Zeile gegen Bestand und vorherige Zeilen geprüft (bei Doppelten gewinnt die frühere Zeile), danach die gültigen Zeilen per `compareByLastName()` sortiert (Nachname, Vorname, Nickname; deutsche Sortierung; ohne Nachname zuletzt) und erst dann die Slots vergeben — die Antwort listet sie in dieser Reihenfolge, Fehlerzeilen danach; `dryRun` für die Vorschau im Frontend — Vorschau und Import nutzen denselben Server-Code.
- Teilnehmer haben `clan` als eigenes Feld; Anzeige- und Spielername ist `displayName()` = `Clan-Nickname` (ohne Clan nur Nickname). DNS-Namen kommen nur aus dem Nickname. Beim Bulk-Import trennt `splitClanNickname()` am ersten Bindestrich. Alte Datensätze ohne `clan` werden als leerer Clan behandelt (`?? ''`).
- **Admin-Login** (`src/auth.ts`): `ADMIN_PASSWORD` gesetzt → `requireAdminForChanges` lässt unter `/api` nur GET/HEAD (außer `/backup`) sowie `/auth`, `/login`, `/logout` ohne Sitzung durch. Sitzung = signiertes Cookie `mcd_admin` (`<ablauf>.<hmac>`, 7 Tage, HMAC-Schlüssel aus dem Passwort). Frontend: `loadAuth()` setzt `body.read-only`, Elemente mit Klasse `admin-only` werden dann ausgeblendet — neue Bearbeiten-Elemente immer mit `admin-only` markieren. `.env` (gitignored) liefert das Passwort für `docker:rebuild`/compose. Login-Sperre: `loginRetryAfter`/`recordLoginFailure` (10 Fehlversuche je `req.ip` in 15 min → 429). Cookie mit `Secure`, wenn `req.secure`.
- **Sicherheit in `server.ts`:** Reihenfolge Security-Header (CSP mit `'unsafe-inline'` wegen `onclick`/`style=`, `frame-ancestors 'none'`) → static → `rejectCrossSite` (CSRF: `Sec-Fetch-Site` cross-site/same-site bzw. fremder `Origin` → 403, gilt auch ohne Passwort) → `requireAdminForChanges` → JSON-Parser (`/api/restore` 10 MB, sonst 3 MB). Der Body wird also erst nach der Anmeldeprüfung gelesen. Kein `cors` — das Frontend ist same-origin. Neue Drittquellen (CDN, externe Bilder) würde die CSP blockieren. Error-Handler: 4xx von body-parser durchreichen, 500 mit Node-`code` ohne Meldung.
- **OPNsense** (`src/opnsense.ts` Logik + HTTP-Client, `src/opnsense-routes.ts`, `public/opnsense.js`): Zugangsdaten als ein Datensatz in Tabelle `opnsense` (Weboberfläche, gilt für alle Events). Das Secret verlässt den Server nie (`settingsView()`), leeres Secret beim Speichern = beibehalten. `/api/opnsense*` ist auch für GET admin-pflichtig (`isProtectedRead` in `auth.ts`). `desiredRecords()` → 3 A-Records pro Teilnehmer, Beschreibung `mcd-brackets #<eventId>: <Anzeigename> (<Bereich>)`; `planSync()` vergleicht mit `search_host_override` (inkl. Aliase in `_children`) → create/update/delete/conflict/unchanged. Nur markierte Einträge werden geändert/gelöscht, Einträge anderer mcd-Events mit gleichem Namen werden übernommen, fremde sind Konflikte. `applyPlan()` ruft danach `unbound/service/reconfigure`. API-Pfade in snake_case wie in den OPNsense-ACLs; geprüft gegen den Quellcode von OPNsense 26.7 (Felder `enabled`, `hostname`, `domain`, `rr`, `server`, `description`). `OpnsenseError` → HTTP 502. Tests mit nachgebautem API-Server in `opnsense.test.ts`.
- **Sitzplan** (`src/seating.ts` rein, `src/seating-store.ts`, `src/seating-routes.ts`, `public/seating.js`, `public/seating-pdf.js`): Tabelle `room` `{ event_id, name, width, height, groups, seats: { "<gruppe>.<b|f><i>": attendeeId } }`. Gruppen: `row` (`x, y, rotation` 0/90/180/270 im Uhrzeigersinn, `length`, `sides` both/one/none — unrotiert laufen die Tische nach rechts, „one“ = Plätze darunter, „both“ zusätzlich darüber) und `area` (Fläche mit Label). `groupShape()` liefert die Zellen relativ zur Gruppe nach Drehung, `describeLayout()` Platznummern (Gruppenreihenfolge, innerhalb Leserichtung) und Überlappungen — die API hängt das als `layout` an jeden Raum, das Frontend rechnet keine Geometrie nach. Platz-Schlüssel hängen an Gruppe+Seite+Index → Verschieben/Drehen ändert die Belegung nie, `keepExistingSeats()` verwirft nur wegfallende Plätze. Auf den Tischen steht nur `nickname` (max. zwei Zeilen per line-clamp, im PDF `nameLines`: erst einzeilig, dann an Wortgrenzen zweizeilig, dann „…“), alles andere im eigenen Tooltip `#seatTooltip` (`showSeatTooltip`, auch über den Stühlen: `<g class="chair" data-key>` aus `chairTables`); im Gestaltungsmodus die Platznummer. PDF: Nickname plus kleine Nummer. Darstellung (Wunsch des Users): Zellen `seat` = nummerierter **Tisch** (wird vergeben), Zellen `table` = **Sitzbereich** mit Stühlen von oben (`chairDirections`/`chairRects` in `seating.js`: Stuhl zeigt zum benachbarten Tisch derselben Gruppe, bei zwei Nachbarn zwei halbe Stühle; das PDF nutzt dieselben Rechtecke) — die internen Namen sind historisch, nur die Optik/Texte zählen. Platznummern sind Strings (`label`): `describeLayout` setzt zuerst `start_label` der Reihe (hochgezählt per `nextLabel`, Ziffer am Ende), dann für den Rest 1, 2, 3 … unter Auslassung belegter Nummern; `number` bleibt die reine Reihenfolge (Sortierung, Schilder). `duplicates` listet doppelte Labels. Frontend zeigt/sucht immer `label`. (Eine Klick-Nummerierung mit `room.labels` gab es kurz — wurde auf Wunsch entfernt, `saveRoom` verwirft Reste.) Reihen haben optional `numbering` (`orderRowSeats`: Seite oben/links zuerst, jede Seite entlang des Tisches — unabhängig von der Drehung; backward/around/around-back). Türen liegen in `room.doors` (eigene Liste, keine Gruppe): `side`, `offset`, `width`, `swing` in/out, `hinge` start/end; `validateDoors` (in der Wand, keine Überlappung), `placeDoor` (nächste Wand zum Klick), `doorSwingCells` — der Schwenkbereich nach innen zählt in `describeLayout` als belegt (Überlappungen) und bei `placeTemplate`. Frontend: Raum = `.room-floor` mit Rand `doorMargins()` (je Seite ≥1 Feld, so breit wie die breiteste Außentür), Türen als SVG (`doorGeometry`), PDF zeichnet Wände/Türen gleich (`drawWallsAndDoors`). Bausteine (`templateGroups`: row, double, u, block, area) erzeugen normale Gruppen, `placeTemplate()` prüft gegen die tatsächlich belegten Zellen (nicht die Rahmen der Gruppen — das Innere einer U-Form ist frei): mit `at` (Klick auf die leere Fläche, Frontend `placeAt`) die nächstgelegene passende Position, sonst die erste freie, bevorzugt mit 1 Feld Abstand. Ein Teilnehmer hat höchstens einen Platz in den **finalen** Räumen eines Events; Räume mit `alternative: true` (Entwürfe) zählen nur gegen sich selbst (`competingRooms` in Store und Frontend: `assignSeat`, `autofillRoom`, „Ohne Platz“, Suche). `updateRoom` mit `alternative: false` gibt die Teilnehmer des Raums in anderen finalen Räumen frei. GET `/events/:id/rooms` blendet Alternativen ohne Admin-Sitzung aus. `clearSeats` (POST `/rooms/:id/clear`) leert die Belegung. `deleteAttendee`/`deleteEvent` in `lan-store.ts` räumen `room` mit auf, `createEvent` kopiert die Räume des letzten Events ohne Belegung; `duplicateRoom()` (POST `/rooms/:id/duplicate`) kopiert einen Raum ins selbe oder ein anderes Event, ebenfalls ohne Belegung (ein Teilnehmer hat nur einen Platz je Event). GET öffentlich. Editor (`seating.js`): schickt immer die komplette Gruppenliste per `PUT /rooms/:id`; Bearbeitungen laufen über `queueEdit()` nacheinander (sonst rechnen schnelle Klicks mit veraltetem Layout); Drehen mehrerer Gruppen um deren gemeinsamen Rahmen; Zoom passt sich automatisch an (`seatZoomAuto`), bis jemand −/+ nutzt. Event-Auswahl teilt `currentEventId`/`ensureCurrentEvent()` mit `lan.js`. PDFs nutzen `SLIP`, `fitFontSize`, `slipLabel`, `slipFileSlug` aus `ip-slips.js`; Platz-Schilder = Tischaufsteller, obere Hälfte per `signFace(..., upper)` um 180° gespiegelt.
- **In Gedenken**: Event-Feld `memorial` (Namen). Sie werden beim Anlegen/Neu-Auslosen nach den Spielern (vor den BYEs) gelost und an der Stage als `memorial_names` gespeichert. `resolveMemorialMatches()` (nach Anlegen und nach jedem Ergebnis) lässt sie jedes spielbare Match per Forfeit verlieren; zwei Gedenk-Einträge gegeneinander → der erste kommt weiter. Ranglisten schließen sie aus. Namen dürfen nicht mit Teilnehmer-Anzeigenamen kollidieren (`assertNotMemorial`).
- Spieler eines Turniers = alle Teilnehmer seines Events als `displayName` (`playerNamesForEvent` liefert `{ players, memorial }`). Änderungen an Clan, Nickname oder Event-Name werden in die Turniere übernommen. `ValidationError` → HTTP 400.
- **Ergebnisse korrigieren** (`src/results.ts`): brackets-manager archiviert ein Match, sobald ein Folge-Match ein Ergebnis hat, und lehnt Änderungen dann ab („The match is locked.“). `followingResults()` sammelt über `manager.find.nextMatches` transitiv alle gespielten Folge-Matches (BYE-Matches werden durchlaufen, aber nicht zurückgesetzt; Round Robin hat keine). `updateMatchResult()` prüft: Gedenk-Match → 400; gleiches Ergebnis → nichts tun; mit Folgeergebnissen ohne `resetFollowing` → 409, sonst `resetResults()` (von hinten nach vorne per `reset.matchResults`), dann `update.match` und `resolveMemorialMatches`. `PUT /api/matches/:id` läuft in `withLock` + `withRollback`. `matchLabel()` → „Winner Bracket · Runde 2 · Match 1“, „Halbfinale …“, „Grand Final“ usw.
- `seeding.ts`: `buildSeeding()` mischt (Fisher-Yates) und füllt SE/DE mit `null` (BYE) auf die nächste Zweierpotenz.
- `standings.ts`: `getStandings()` → Platzierung + `pending` + `points`. DE/SE über `calculatePlacements()` (DE: höchste erreichte Gruppe → letztes Match gewonnen/verloren → Runde → Wins → Losses), RR über `manager.get.finalStandings` mit 3/1/0.
- Routen: `GET/POST /api/stages`, `GET/DELETE /api/stages/:id`, `POST /api/stages/:id/regenerate`, `GET /api/stages/:id/matches`, `GET /api/matches`, `PUT /api/matches/:id`, `GET/POST /api/participants`, `DELETE /api/participants/:id`, `GET /api/viewer-data/:stageId`, `GET /api/standings/:stageId`, `GET /api/backup`, `POST /api/restore`.

**Frontend** — `public/index.html`, `public/app.js`, `public/styles.css`. Kein Build-Step, keine Module; Funktionen sind global und werden per `onclick` im HTML aufgerufen. Drittlibs liegen lokal in `public/lib/` (bewusst kein CDN).
- **Jede Nutzerangabe in `innerHTML`-Templates durch `escapeHtml()`**. Strings für `onclick` über `data-*`-Attribute übergeben, nicht in JS-String-Literale einbetten.
- Icons: SVG-Sprite am Anfang von `index.html` (`<symbol id="i-…">`), im JS per `icon('name')`. Keine Emojis als Icons.
- Styling: Design-Tokens als CSS-Variablen in `:root` von `styles.css`. Optik (Wunsch des Users: nicht nach Standard-AI-UI, ruhig farbig): Anthrazit statt Navy, kleine Radien, harte Schatten, keine Glow-Verläufe/Blur, keine Versal-Mini-Labels; Farbstreifen (Orange/Pink/Cyan/Lime) unter Topbar und über Footer. Überschriften, Tabs, Buttons, Badges in `--font-display` (Chakra Petch, lokal in `public/lib/fonts/`, kommt per `npm run vendor` aus `@fontsource/chakra-petch`). Jeder Bereich hat eine Farbe `--view-color` (`body[data-view]`, gesetzt in `showView()`: Teilnehmer Cyan, Sitzplan Lime, Turniere Orange) für Karten-Oberkante, Überschrift-Icons und aktive Tabs; Orange `--primary-color` = `#ff4500` (Farbe des mcd.lan-Logos) ist die Hauptakzentfarbe und Farbe der Hauptaktionen (`btn-primary`), Text darauf weiß (`--on-primary`); PDFs nutzen dasselbe Orange (`SLIP.accent`). Turniermodi: DE Orange, SE Cyan, RR Violett (`--type-color`). Clans als farbige `clan-tag` (`clanTag()` in `lan.js`, Farbe nach alphabetischer Reihenfolge der Clans im Event, 6 Klassen `clan-c0…5`). Nur hex/rgba-Farben — html2canvas (Export) versteht kein `color-mix()`/`oklch()`. Export-Hintergrund `EXPORT_BACKGROUND` in `app.js` muss zu `--bg-color` passen.
- Buttons mit Icon: veränderlichen Text in `<span class="btn-label">` legen und per `setButtonLabel()` ändern, nie `textContent` des Buttons setzen.
- Layout: einspaltig. Oben einklappbare Karten („Neues Turnier“ bzw. Event-Leiste mit „Konfiguration“) über `toggleSection(id, open?)`; der Zustand wird in `localStorage` gemerkt (`COLLAPSIBLE_SECTIONS` in `app.js`).
- Teilnehmerliste: getrennte Spalten Vorname/Nachname/Clan/Nickname, sortierbar über `th.sortable[data-sort]` (`attendeeSort`), Filter per Suche und Clan-Auswahl (`__all__` = alle, `''` = ohne Clan).
- Footer: feste Leiste am unteren Fensterrand (`position: fixed`); `app.js` schreibt seine Höhe per `ResizeObserver` nach `--footer-height`, `.container` hält unten so viel Platz frei. `server.ts` ersetzt in `index.html` die Platzhalter `{{APP_VERSION}}` (aus `package.json`) und `{{REPO_URL}}` (aus `repository.url`, ohne `.git`). Statistik und Update-Hinweis kommen aus `GET /api/info` (`src/info.ts`): `startUpdateChecks()` holt beim Start und alle 6 h die GitHub-Tags (Fehler/offline werden still ignoriert, letzter Stand bleibt), `compareVersions()` (Release > Pre-Release). Gespielte Matches = abgeschlossen, beide Seiten bekannt, kein Forfeit (`isPlayedMatch`). Das Frontend lädt die Infos per `refreshFooter()` (entprellt) nach `loadStages`/`loadMatches`/`loadAttendees`.
- Cache-Busting: `server.ts` liefert `index.html` selbst aus (`no-store`) und hängt an alle JS/CSS-URLs `?v=<version>-<startzeit>` — neue Script-/CSS-Dateien in `index.html` werden automatisch erfasst, solange sie als `src="datei.js"` bzw. `href="datei.css"` (optional unter `lib/`) eingebunden sind.
- Globaler State: `stages`, `matches`, `participants` (via `loadStages/loadMatches/loadParticipants`).
- Drei Ansichten per Hash: `#turniere` (Standard), `#teilnehmer` und `#sitzplan` (`showView()`, Zuordnung in `VIEWS`). Teilnehmer-Verwaltung in `public/lan.js`, nutzt `apiFetch`, `escapeHtml`, `icon`, `openModal`/`closeModal` und `lanEvents` aus `app.js`.
- IP-Zettel: `public/ip-slips.js` zeichnet per jsPDF ein Vektor-PDF (A4, eine Seite pro Teilnehmer; `buildSlipsPdf(event, attendees)`). Nur jsPDF-Standardschriften (helvetica/courier, WinAnsi: Umlaute ok, keine Emojis/Sonderzeichen außerhalb Latin-1). Subnetzmaske, Router/Gateway und DNS stehen immer drauf (leer = Linie zum Ausfüllen); die Domain nicht (sie steckt nur in den DNS-Namen). Optionales Event-Logo (`logo`, PNG/JPEG-Data-URL, Upload im Browser zu PNG ≤1000 px konvertiert; erscheint auch oben links in der Topbar statt der generischen Grafik — `updateBrandLogo()` in `app.js`, Logo des gewählten Events, aufgerufen von `loadEvents` und den Event-Auswahlen in `lan.js`/`seating.js`) oben rechts im Seitenverhältnis des Bildes (`logoBox()`: Hoch-, Quer- oder Quadratformat bei etwa gleicher Fläche, max. 64 × 48 mm; die Adressen rücken unter das Logo; Vorschau in der Konfiguration ebenso).
- Anleitung feste IP (`public/ip-guide.js`, Button „Anleitung (PDF)“, `exportIpGuide()`): je eine A4-Seite Windows (klassische Dialoge `ncpa.cpl` › Ethernet › TCP/IPv4) und macOS (Systemeinstellungen › Netzwerk › Details › TCP/IP/DNS). Die Dialoge sind per jsPDF nachgezeichnete Vektor-Mock-ups (`win*`/`mac*`), gefüllt mit Maske/Gateway/DNS des Events; die IP steht als „vom IP-Zettel“ drin. Orange nummerierte Marker (`guideMarker`) verbinden Schritte und Mock-ups. Gleicher Stil/Helfer wie die IP-Zettel.
- **Druckrand:** Alle PDFs halten mind. 5 mm Abstand zur Blattkante (nicht randlos druckbar). Zettel-Inhalte liegen innerhalb `SLIP.margin` (18 mm); Bracket/Rangliste über `addCanvasToPdf()` in `app.js` (`PRINT_MARGIN_MM`, A4, Rangliste ggf. mehrseitig).
- Mit `let` deklarierte Globals (z.B. `attendees`) hängen nicht an `window` — in Tests per `iframe.contentWindow.eval(...)` ansprechen.
- `createTournament` schickt nur Event + Modus (Spieler kommen vom Server); `resetBracket` → `regenerateStage()` → `POST /api/stages/:id/regenerate`.
- `viewBracket` (brackets-viewer, Click-to-Win → `showQuickWinnerSelection` → `selectWinner` → `updateMatchQuick`), `viewRankings`/`viewEventRankings` → `fetchStandings()` + `showRankings()`. Ergebnis eines abgeschlossenen Matches ändern → `prepareCorrection()` holt `GET /matches/:id/following`, `renderCorrection()` zeigt `#correctionPanel` über dem Bracket, `highlightCorrection()` markiert `.match[data-match-id]` (`is-correction-target`/`is-correction-affected`; CSS steht hinter der grünen Kante abgeschlossener Matches). Das Bracket bleibt unverändert, bis `applyCorrection()` → `updateMatchQuick(…, resetFollowing = true)`.
- Export: `exportBracketAsImage/Pdf`, `exportRankingsAsImage/Pdf` (html2canvas + jsPDF).

## Domänenlogik

- **Punktesystem** global, anpassbar: `src/points.ts` (`DEFAULT_POINTS` = Platz 1–10 + `rest` für ab Platz 11, `validatePoints`, `pointsFromRecord` → bei kaputtem Datensatz die Standardwerte), gespeichert als ein Datensatz in Tabelle `points` (fehlt = Standard), `GET/PUT /api/points` in `points-routes.ts` (`loadPoints()`). `getStandings(…, pointsConfig)` rechnet die Punkte bei jedem Abruf aus der Platzierung, deshalb wirkt eine Änderung sofort auf alle Turniere, nichts wird gespeichert oder migriert. Frontend: Karte „Punktesystem“ in `#turniere` (`renderPoints`, Standardwert unter jedem Feld, `is-changed`), nach dem Speichern lädt `refreshOpenRankings()` eine offene Rangliste neu. Bei geänderten Standardwerten die README-Tabelle mitpflegen.
- **Event-Rankings** aggregiert der Browser: alle Stages mit gleichem `event_name` → je `/api/standings` → `points` pro Teilnehmername summieren.
- `event_name` ist ein **eigenes Feld** an der Stage (nicht Teil von brackets-manager) und wird nach `manager.create.stage` per `storage.update` ergänzt.
- Ein Turnier = eine Stage; Participants hängen per `tournament_id` daran. Die Turnier-ID vergibt der Server (`max+1` im Lock). Stage-IDs werden von brackets-manager nach dem Löschen wiederverwendet.
- Round Robin braucht `groupCount`; `createStage()` setzt standardmäßig 1.
- Datenmodell `db.json`: `participant`, `stage`, `group`, `round`, `match`, `match_game` (brackets-manager) plus `event`, `attendee`, `opnsense`, `room`, `points` (`APP_TABLES`).

## Konventionen

- UI-Texte, README und Commit-Messages auf Deutsch. Commit-Stil: `chore: …`, `fix: …` bzw. Release-Commits `vX.Y.Z-beta: …`.
- Version steht in `package.json` **und** README (`**Version:**`) — beide aktualisieren.
- Deployment: GitHub Action baut Multi-Arch-Image nach `ghcr.io/lordimac/mcd.brackets` bei Push auf `main` und `v*`-Tags.
- Laufzeitdaten liegen in `data/` (gitignored, Docker-Volume `/app/data`). Nie echte `db.json` committen.
- Die `db.json` im Repo-Root (gitignored) enthält echte Altdaten (Event „mcd.lan 2025“), nicht löschen.

## Bekannte Grenzen

- OPNsense-Abgleich ist nur gegen eine nachgebaute API getestet, nicht gegen eine echte Firewall.
- Zugriffskontrolle nur über ein gemeinsames Admin-Passwort (keine Benutzerkonten); Lesen ist immer öffentlich (auch Vor-/Nachnamen und Exporte — bewusst so). Sitzungen sind zustandslos: Logout löscht nur das Cookie, ungültig werden Tokens erst nach Ablauf oder Passwortwechsel. Login-Sperre nur im Speicher (Neustart setzt sie zurück). OPNsense-Secret liegt im Klartext in `db.json` und im Backup. HTTPS übernimmt ggf. ein Reverse-Proxy.
- Event-Rankings fassen Teilnehmer über den Namen zusammen; Tippfehler ergeben getrennte Einträge.
