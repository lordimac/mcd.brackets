# CLAUDE.md

Turnierverwaltung (Single/Double Elimination, Round Robin) mit Event-basiertem Meisterschafts-Punktesystem. Express-Backend auf Basis von `brackets-manager`, Vanilla-JS-Frontend mit `brackets-viewer`.

## Befehle

```bash
npm install
npm run server         # Dev-Server (tsx src/server.ts) → http://localhost:3000
npm run server:watch   # Dev mit tsx watch Auto-Reload
npm test               # Node-Testrunner über tsx (src/**/*.test.ts)
npm run build          # tsc (TypeScript 7, nativ) → dist/ — Typprüfung inkl. Tests
npm start              # node dist/server.js
npm run vendor         # kopiert brackets-viewer, html2canvas, jsPDF aus node_modules nach public/lib/
npm run docker:rebuild # Image bauen + Container mcd-brackets neu erstellen (Port 3001, ./data)
```

- **Nach jeder abgeschlossenen Änderung `npm run docker:rebuild` ausführen** (Wunsch des Users). Port 3000 ist durch einen anderen Container belegt. Das Skript baut über den buildx-Builder `mcd-dns` mit festen DNS-Servern (`scripts/buildkitd.toml`), weil die DNS-Auflösung in Docker Desktop hier nicht funktioniert und `docker build`/`docker compose build` bei `npm ci` hängen bleiben.

- Umgebungsvariablen: `PORT` (3000), `DATA_DIR` (`./data`), `ADMIN_PASSWORD`, `UPDATE_CHECK` (`false` = kein Versionscheck), `TRUST_PROXY` (Express `trust proxy`, Default aus). Für manuelle Tests einen Server mit eigenem `DATA_DIR` und Port starten, nie gegen die echte `data/db.json` schreiben.
- Nach jedem Update von brackets-viewer/html2canvas/jspdf `npm run vendor` ausführen — der Browser lädt nur die Kopien in `public/lib/`.
- Node 24 LTS (`.nvmrc`, `engines`, Docker `node:24-alpine`; `docker:rebuild` baut mit `--pull`). Container läuft als `node` (UID 1000).
- TypeScript 7 hat keine JS-Compiler-API mehr → kein `ts-node`; Ausführung von TS-Dateien über `tsx`.
- `package.json` erzwingt per `overrides` `uuid@^11.1.1` (Sicherheitsfix für brackets-manager).
- `brackets-model` ist devDependency, nur für Typen (`import type`); Ausnahme: Tests importieren `Status`.

## Architektur

**Backend** (`src/`):
- `db.ts`: `JsonDatabase` (brackets-json-db → node-json-db, hält Daten **im Speicher**) auf `DATA_DIR/db.json`, typisiert als `CrudInterface` (die eigenen Typen von JsonDatabase sind zu lose). Immer über `getStorage()`/`getManager()` zugreifen, nie Instanzen cachen — `replaceDatabase()` erzeugt sie neu. Das Speichern übernimmt `db.ts` selbst (`save()` der internen node-json-db ersetzt in `openDatabase()`): immer atomar (`.tmp` + fsync + rename), außerhalb eines Locks sofort, innerhalb von `withLock()` (serialisiert alle schreibenden Routen) gesammelt einmal am Ende; scheitert das Schreiben, lädt der Speicher den Stand der Datei neu. `withRollback()` nimmt den Snapshot **aus dem Speicher** (die Datei hat im Lock noch den alten Stand — verschachtelte Rollbacks, z. B. je Turnier in `syncEventStages`, dürfen die äußere Änderung nicht verwerfen). `getRevision()` zählt jede Änderung (Cache `identityData()` in `welcome-routes.ts`). `getAppStore().insert` wirft, statt wie brackets-json-db `-1` zu liefern (für `participant` in `stage-sync.ts`: `insertParticipant`). IDs vergibt brackets-json-db als `max+1` — nach dem Löschen des höchsten Datensatzes wird die ID wiederverwendet, Verweise darauf beim Löschen aufräumen.
- `server.ts`: Routen. Fehler per `throw new HttpError(status, msg)`; Express 5 leitet abgelehnte Promises an den JSON-Error-Handler am Ende weiter (keine try/catch in Routen nötig).
- `stages.ts`: `createStage()`/`deleteStage()`/`findStage()` — gemeinsame Bausteine für Anlegen, Neu-Erzeugen und Löschen. Beim Ergänzen von `event_name` die Stage **frisch aus dem Storage lesen**: das Rückgabeobjekt von `create.stage` hat kein `settings.seedOrdering`, ein Zurückschreiben würde es löschen und Double Elimination unspielbar machen (Regressionstest `stages.test.ts`).
- `lan.ts` (reine Logik), `lan-store.ts` (Persistenz), `lan-routes.ts` (Router unter `/api`): Events mit Domain, DNS-Server und 3 IP-Bereichen; Teilnehmer (`attendee`) mit `slot` → IP *i* = `ranges[i].start + slot`, DNS-Namen `hostname`, `hostname2`, `hostname3` (+ `.domain`). Nickname und alle abgeleiteten DNS-Namen sind je Event eindeutig. Tabellen `event`/`attendee` liegen in derselben `db.json` (über `getAppStore()`, `ensureAppTables()` legt sie an). `syncEventsFromStages()` erzeugt Event-Datensätze für alte Turniere (beim Start und nach Restore).
- Bulk-Import `importBulk()`: Zeilen `Nachname, Vorname // Clan-Nickname` (`parseBulkLine`), jede Zeile gegen Bestand und vorherige Zeilen geprüft (bei Doppelten gewinnt die frühere Zeile), danach die gültigen Zeilen per `compareByLastName()` sortiert (Nachname, Vorname, Nickname; deutsche Sortierung; ohne Nachname zuletzt) und erst dann die Slots vergeben — die Antwort listet sie in dieser Reihenfolge, Fehlerzeilen danach; `dryRun` für die Vorschau im Frontend — Vorschau und Import nutzen denselben Server-Code.
- Teilnehmer haben `clan` als eigenes Feld; Anzeige- und Spielername ist `displayName()` = `Clan-Nickname` (ohne Clan nur Nickname). DNS-Namen kommen nur aus dem Nickname. Beim Bulk-Import trennt `splitClanNickname()` am ersten Bindestrich. Alte Datensätze ohne `clan` werden als leerer Clan behandelt (`?? ''`).
- **Admin-Login** (`src/auth.ts`): `ADMIN_PASSWORD` gesetzt → `requireAdminForChanges` lässt unter `/api` nur GET/HEAD (außer `/backup`) sowie `/auth`, `/login`, `/logout` ohne Sitzung durch. Sitzung = signiertes Cookie `mcd_admin` (`<ablauf>.<hmac>`, 7 Tage, HMAC-Schlüssel aus dem Passwort). Frontend: `loadAuth()` setzt `body.read-only`, Elemente mit Klasse `admin-only` werden dann ausgeblendet — neue Bearbeiten-Elemente immer mit `admin-only` markieren. `.env` (gitignored) liefert das Passwort für `docker:rebuild`/compose. Login-Sperre: `loginRetryAfter`/`recordLoginFailure` (10 Fehlversuche je `req.ip` in 15 min → 429). Cookie mit `Secure`, wenn `req.secure`.
- **Sicherheit in `server.ts`:** Reihenfolge Security-Header (CSP mit `'unsafe-inline'` wegen `onclick`/`style=`, `frame-ancestors 'none'`) → static → `rejectCrossSite` (CSRF: `Sec-Fetch-Site` cross-site/same-site bzw. fremder `Origin` → 403, gilt auch ohne Passwort) → `requireAdminForChanges` → JSON-Parser (`/api/restore` 10 MB, sonst 3 MB). Der Body wird also erst nach der Anmeldeprüfung gelesen. Kein `cors` — das Frontend ist same-origin. Neue Drittquellen (CDN, externe Bilder) würde die CSP blockieren. Error-Handler: 4xx von body-parser durchreichen, 500 mit Node-`code` ohne Meldung.
- **OPNsense** (`src/opnsense.ts` Logik + HTTP-Client, `src/opnsense-routes.ts`, `public/opnsense.js`): Zugangsdaten als ein Datensatz in Tabelle `opnsense` (Weboberfläche, gilt für alle Events). Das Secret verlässt den Server nie (`settingsView()`), leeres Secret beim Speichern = beibehalten. `/api/opnsense*` ist auch für GET admin-pflichtig (`isProtectedRead` in `auth.ts`). `desiredRecords()` → 3 A-Records pro Teilnehmer, Beschreibung `mcd-brackets #<eventId>: <Anzeigename> (<Bereich>)`; `planSync()` vergleicht mit `search_host_override` (inkl. Aliase in `_children`) → create/update/delete/conflict/unchanged. Nur markierte Einträge werden geändert/gelöscht, Einträge anderer mcd-Events mit gleichem Namen werden übernommen, fremde sind Konflikte. `applyPlan()` ruft danach `unbound/service/reconfigure`. API-Pfade in snake_case wie in den OPNsense-ACLs; geprüft gegen den Quellcode von OPNsense 26.7 (Felder `enabled`, `hostname`, `domain`, `rr`, `server`, `description`). `OpnsenseError` → HTTP 502. Tests mit nachgebautem API-Server in `opnsense.test.ts`.
- **Willkommens-Seite** (`src/welcome.ts` rein, `src/welcome-routes.ts`, `public/welcome.js`): Startansicht `#willkommen` (leerer/unbekannter Hash; Bereichsfarbe Weiß, Reiter mobil „Start“ über `.tab-long`/`.tab-short`). `GET /api/whoami` (öffentlich, `no-store`; `?ip=` nur Admins → Testansicht) erkennt das Gerät über `req.ip` (`clientIPv4` entfernt `::ffff:`): `identify()` geht die Events mit `ip_identification !== false` durch (`preferredEvents`: laufendes Event zuerst, dann neueste ID), das erste Event, dessen Bereiche die IP enthalten, entscheidet → `identified` / `unassigned` (im Bereich, kein Teilnehmer) / `unknown` / `disabled` (alle Events aus) / `no-event`. `networkChecks()`: IP, Gateway im Subnetz (Maske+Gateway), DNS (Route fragt per `dns/promises` `Resolver` den `dns_server` des Events, 1,5 s; nicht erreichbar → Check fehlt). Maske/Gateway/DNS des Geräts selbst sieht der Server nicht. Event-Feld `ip_identification` (Standard an, fehlt bei alten Events = an, `createEvent` übernimmt es vom letzten Event), Schalter im Konfigurationsblock „Netzwerk“. Frontend-Global `me` (Antwort von whoami, `loadWhoami()` entprellt) + `isMe(attendeeId)`: Chip `#meChip` in der Topbar, `tr.is-me` in der Teilnehmerliste, `.cell-seat.is-me` im Sitzplan, `markOwnParticipant()` in `viewBracket`. Layout: über 960 px steht die Ausweis-Karte in der linken Drittelspalte (`.welcome-columns` > `.welcome-main`), alle übrigen Blöcke rechts in `.welcome-side` (2/3), darunter eine Spalte; kein Event-Logo in der Karte (steht in der Topbar). Reihenfolge: Ausweis (Kachel „Nächstes Match“ `#welcomeNextMatch`, gefüllt von `renderNextMatchFact()` über `nextMatchOf()`/`compareNextMatches()` — spielbar zuerst, dann nach Zeit), „Deine Turniere“, Netzwerk-Check, Shares. Nicht erkannte Geräte (`unknown`/`unassigned`) sehen statt eines Fehlerberichts einen Check-in (`.welcome-checkin`: „Willkommen bei <Event>!“, drei Schritte `.checkin-steps` — IP-Zettel holen, Adresse einstellen mit Sprung zu `#welcomeSetup` und Anleitung-PDF, neu laden — und Links zum Stöbern). Netzwerk-Check: alle Prüfungen bestanden → zugeklapptes `<details class="welcome-network">` „Netzwerk ok“; nicht erkannte Geräte bekommen „So richtest du dein Gerät ein“ und Fehler als Schritte (`is-todo`, blau) statt rot. „Hallo …“/„Willkommen!“ ist das `h1` der Ansicht (die Marke in der Topbar ist kein Heading). „Deine Turniere“ lädt `/stages`, `/participants`, je Turnier Matches/Schedule/Standings selbst und sortiert spielbare Matches zuerst (`compareNextMatches`), dann wartende, dann den Rest; die Karte mit spielbarem Match bekommt `.is-mine` und „Zu meinem Match“. `refreshMeHighlights()` rendert die Turnier-Reiter nach jeder Erkennung neu (auch wenn gerade eine andere Ansicht offen ist). Sitzplatz-Sprung über `pendingSeatJump` in `seating.js`. „Ansicht testen“ ist ein zugeklapptes `<details id="welcomeTestBox">` (bleibt offen, solange getestet wird). Hinter Docker Desktop sieht der Server nicht die echte Client-IP. **Admin per IP:** Teilnehmer-Feld `admin` (fehlt = nein; Haken nur im Bearbeiten-Dialog; `updateAttendee` ohne `admin` im Input behält den Wert, `importAttendees` kopiert ihn nie). `resolveIpAdmin` (welcome-routes.ts, in server.ts zwischen `rejectCrossSite` und `requireAdminForChanges`, nur bei gesetztem Passwort) nutzt dasselbe `identify()` → `markIpAdmin(req)` (WeakSet in auth.ts); `adminVia(req)` → `open`/`ip`/`session`/null, `isAdmin` = `adminVia !== null`, `/api/auth` liefert `via` (Frontend zeigt Abmelden nur bei `session`). `GET /events/:id/attendees` entfernt `admin` für Nicht-Admins. Bewusst in Kauf genommen: IP-Adressen sind im LAN fälschbar.
- **Sitzplan** (`src/seating.ts` rein, `src/seating-store.ts`, `src/seating-routes.ts`, `public/seating.js`, `public/seating-pdf.js`): Tabelle `room` `{ event_id, name, width, height, groups, seats: { "<gruppe>.<b|f><i>": attendeeId } }`. Gruppen: `row` (`x, y, rotation` 0/90/180/270 im Uhrzeigersinn, `length`, `sides` both/one/none — unrotiert laufen die Tische nach rechts, „one“ = Plätze darunter, „both“ zusätzlich darüber) und `area` (Fläche mit Label). `groupShape()` liefert die Zellen relativ zur Gruppe nach Drehung, `describeLayout()` Platznummern (Gruppenreihenfolge, innerhalb Leserichtung) und Überlappungen — die API hängt das als `layout` an jeden Raum, das Frontend rechnet keine Geometrie nach. Platz-Schlüssel hängen an Gruppe+Seite+Index → Verschieben/Drehen ändert die Belegung nie, `keepExistingSeats()` verwirft nur wegfallende Plätze. Auf den Tischen steht nur `nickname` (nie mitten im Wort getrennt: mehrere Wörter max. zwei Zeilen per line-clamp, ein Wort einzeilig `.is-one-word`, Rest „…“, mind. 0,7 rem; Tische kleiner als `SEAT_NAME_MIN_UNIT` (48 px, Handy) zeigen stattdessen die Platznummer `.seat-label`; vergeben = grüner Rahmen, eigener Platz orange gefüllt mit Legenden-Eintrag `#legendMe`; im PDF `nameLines`: erst einzeilig, dann an Wortgrenzen zweizeilig, dann „…“), alles andere im eigenen Tooltip `#seatTooltip` (`showSeatTooltip`, auch über den Stühlen: `<g class="chair" data-key>` aus `chairTables`); im Gestaltungsmodus die Platznummer. Reihen haben optional `numbering` (`orderRowSeats`: Seite oben/links zuerst, jede Seite entlang des Tisches — unabhängig von der Drehung; backward/around/around-back). Türen liegen in `room.doors` (eigene Liste, keine Gruppe): `side`, `offset`, `width`, `swing` in/out, `hinge` start/end; `validateDoors` (in der Wand, keine Überlappung), `placeDoor` (nächste Wand zum Klick), `doorSwingCells` — der Schwenkbereich nach innen zählt in `describeLayout` als belegt (Überlappungen) und bei `placeTemplate`. Frontend: Raum = `.room-floor` mit Rand `doorMargins()` (je Seite ≥1 Feld, so breit wie die breiteste Außentür), Türen als SVG (`doorGeometry`), PDF zeichnet Wände/Türen gleich (`drawWallsAndDoors`). Bausteine (`templateGroups`: row, double, u, block, area) erzeugen normale Gruppen, `placeTemplate()` prüft gegen die tatsächlich belegten Zellen (nicht die Rahmen der Gruppen — das Innere einer U-Form ist frei): mit `at` (Klick auf die leere Fläche, Frontend `placeAt`) die nächstgelegene passende Position, sonst die erste freie, bevorzugt mit 1 Feld Abstand. Ein Teilnehmer hat höchstens einen Platz in den **finalen** Räumen eines Events; Räume mit `alternative: true` (Entwürfe) zählen nur gegen sich selbst (`competingRooms` in Store und Frontend: `assignSeat`, `autofillRoom`, „Ohne Platz“, Suche). `updateRoom` mit `alternative: false` gibt die Teilnehmer des Raums in anderen finalen Räumen frei. GET öffentlich. Flächen (`area`) sind vollflächig getönt, nicht schraffiert. Modi (`seatMode`, Admins): `view` „Ansehen“ (Standard, Tippen zeigt nur den Tooltip — wie für Nicht-Admins, gegen versehentliches Vergeben), `assign` „Plätze vergeben“, `layout` „Raum gestalten“; `#seatPlanCard.is-view`. Bereichsfarbe Braun. - **SMB-Shares** (`src/shares.ts` rein, `src/share-routes.ts`, `public/shares.js`): Teilnehmer-Feld `shares` (`range_index` → Host = `ips[i]`) und Event-Feld `shares` (`host` = IPv4 oder DNS-Name), je `{ id, label, path ("share/ordner"), username, password }`; fehlt = keine. Eigene Routen `PUT /attendees/:id/shares` (öffentlich in `isPublicWrite`, Route prüft Admin oder `ipAttendeeId(req)` — liegt in `welcome-routes.ts`, nutzt auch der Burger; Body-Limit 20 kB) und `PUT /events/:id/shares` (Admin), immer die komplette Liste. ## Domänenlogik

- **Punktesystem** global, anpassbar: `src/points.ts` (`DEFAULT_POINTS` = Platz 1–10 + `rest` für ab Platz 11, `validatePoints`, `pointsFromRecord` → bei kaputtem Datensatz die Standardwerte), gespeichert als ein Datensatz in Tabelle `points` (fehlt = Standard), `GET/PUT /api/points` in `points-routes.ts` (`loadPoints()`). `getStandings(…, pointsConfig)` rechnet die Punkte bei jedem Abruf aus der Platzierung, deshalb wirkt eine Änderung sofort auf alle Turniere, nichts wird gespeichert oder migriert. Frontend: Karte „Punktesystem“ in `#turniere` (`renderPoints`, Standardwert unter jedem Feld, `is-changed`), nach dem Speichern lädt `refreshOpenRankings()` eine offene Rangliste neu. Bei geänderten Standardwerten die README-Tabelle mitpflegen.
- **Event-Rankings** aggregiert der Browser: alle Stages mit gleichem `event_name` → je `/api/standings` → `points` pro Teilnehmername summieren.
- `event_name` ist ein **eigenes Feld** an der Stage (nicht Teil von brackets-manager) und wird nach `manager.create.stage` per `storage.update` ergänzt.
- Ein Turnier = eine Stage; Participants hängen per `tournament_id` daran. Die Turnier-ID vergibt der Server (`max+1` im Lock). Stage-IDs werden von brackets-manager nach dem Löschen wiederverwendet.
- Round Robin braucht `groupCount`; `createStage()` setzt standardmäßig 1.
- Datenmodell `db.json` (Stage-Felder der App u. a. `event_name`, `schedule`, `memorial_*`, `closed_at`): `participant`, `stage`, `group`, `round`, `match`, `match_game` (brackets-manager) plus `event`, `attendee`, `opnsense`, `room`, `points`, `timetable`, `burger_menu`, `burger_order` (`APP_TABLES`). SMB-Shares hängen an `event`/`attendee`.

## Konventionen

- Turnierbegriffe in der Oberfläche deutsch: K.-o.-System, Doppel-K.-o., Jeder gegen jeden, Gewinnerrunde, Verliererrunde, Großes Finale (Rückspiel), Freilos (`formatType()`, `BRACKET_LOCALE_DE`, `roundLabel()`/`matchLabel()`). Im Code bleiben die englischen Bezeichner (`winner bracket`, `grand final`). Gespeicherte Rundennamen in `stage.schedule` bringt `relabelSchedules()` (schedule.ts) beim Start und nach Restore auf den aktuellen Stand.
- UI-Texte, README und Commit-Messages auf Deutsch. Commit-Stil: `chore: …`, `fix: …` bzw. Release-Commits `vX.Y.Z-beta: …`.
- Version steht in `package.json` **und** README (`**Version:**`) — beide aktualisieren.
- Deployment: GitHub Action baut Multi-Arch-Image nach `ghcr.io/lordimac/mcd.brackets` bei Push auf `main` und `v*`-Tags.
- Laufzeitdaten liegen in `data/` (gitignored, Docker-Volume `/app/data`). Nie echte `db.json` committen.
- Die `db.json` im Repo-Root (gitignored) enthält echte Altdaten (Event „mcd.lan 2025“), nicht löschen.

## Bekannte Grenzen

- OPNsense-Abgleich ist nur gegen eine nachgebaute API getestet, nicht gegen eine echte Firewall.
- Zugriffskontrolle nur über ein gemeinsames Admin-Passwort (keine Benutzerkonten); Lesen ist immer öffentlich (auch Vor-/Nachnamen und Exporte — bewusst so). Sitzungen sind zustandslos: Logout löscht nur das Cookie, ungültig werden Tokens erst nach Ablauf oder Passwortwechsel. Login-Sperre nur im Speicher (Neustart setzt sie zurück). OPNsense-Secret liegt im Klartext in `db.json` und im Backup. HTTPS übernimmt ggf. ein Reverse-Proxy.
- Event-Rankings fassen Teilnehmer über den Namen zusammen; Tippfehler ergeben getrennte Einträge.
